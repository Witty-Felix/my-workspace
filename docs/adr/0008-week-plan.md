# 周规划：悬在周轴之上的一个浮窗，与「安排」是两张不同的表

工作台只有一种内容单位「安排」时，用户想写「这周只干三件事」这类不落到具体某天某时段的话，没有地方放。硬塞成安排会污染周轴（得编一个日期、一个时段），也会让「完成」语义混起来——安排的完成是「这件事发生了」，规划的完成是「这周的重点推进了」。

决定：**周规划独立于安排，是第二个内容单位，只归属到某一 ISO 周。**

## 决定

- **一条规划也是一条记录**：`{ id, week, title, note?, doneAt?, order, createdAt, updatedAt }`。`week` 是 `2026-W46` 形式的 ISO 周标识；规划没有 `date` / `slot`，永远不进周轴。
- **字段名与词表的对应**（CODING_STANDARDS《数据》要求 ADR 写明）：
  - `plans`（磁盘数组） ↔ 「周规划」这一整个概念
  - `plans[]` 的每一条 ↔ 「规划条目」
  - `title` ↔ 条目的标题（界面文案「这一条要做什么」）
  - `note` ↔ 条目的备注
  - `week` ↔ 「周」（GLOSSARY 已定义 ISO 周）
  - `order` ↔ 同一周内的先后（与「安排」的 `order` 同义）
  - `doneAt` / `done` ↔ 「完成」状态与「划掉」动作（沿用 ADR-0007，`done` 只是接口入参名）
  - 界面上承载它的浮窗 ↔ 「规划窗」
- **存在同一个 `data.json` 里，但独立成 `plans` 数组**。不用 `{"2026-W46": [...]}` 这种以周为键的对象——那会逼着每一次读写都做「这一周存在吗」的判断，也让「按 order 排序」这种通用逻辑无处安放。
- **磁盘上 `plans` 是可选的、稀疏的**：没有规划时整个字段不写。`envelope()` 在内存里始终给 `plans: []`（调用方不必判空），落盘时由 `forDisk()` 把空的省掉。这是「稀疏字段」规则在**磁盘**上的落地，不是内存上的。
- **版本号仍是 1，不写迁移**：老数据没有 `plans`，读出来就是空数组，语义正确。ADR-0007 之后第二次只加可选字段。
- **接口三个动词 + 一个顺路带回**：
  - `GET /api/plan?week=` 取某一周
  - `POST /api/plan` 加一条（`week` + `title` 必填）
  - `PATCH /api/plan/:id` 改标题 / 备注 / 完成
  - `DELETE /api/plan/:id`
  - `GET /api/items?from&to&week=` 顺路带回 `plan`（可选字段，没规划就没有这个键）。翻周本来就要发这一趟，多带一个字段比再发一次请求省一个往返——跨境链路上这是 1~2 秒。
- **完成沿用 ADR-0007 的 `doneAt`**：有就是已完成，取消就删字段。`done` 只是接口入参名。划掉的视觉是标题与备注一起加删除线。
- **`week` 显式传，不从 `from` 推**：`from` 是周一这件事是界面约定，不该让接口去猜。`isWeek()` 校验 `YYYY-Www` 且周数 1–53。
- **备注保留换行**：`cleanNote()` 与 `cleanText()` 分开。规划的文字允许换行，压平会把「① ② ③」挤成一行。
- **界面是浮窗（素纸）**：`position:fixed`，拖标题栏移动，图钉置顶（`z-index` 45 → 60），最小化只留标题栏，右下角可缩放。位置只记在内存，刷新回默认位。
- **手机端不是浮窗，是两页**：窄屏（≤900px）下顶栏 `.nav` 是 `display:none`，桌面那个「规划」按钮在手机上根本不存在；390px 也装不下 372px 的浮窗，把手更点不准。所以手机走独立渲染路径：`规划 / 当天` 两个标签整页切换，规划独占一页。数据、写队列、点按阈值与桌面共用。
- **点按与滑动靠位移阈值区分**：`pointerdown` 只记起点，`pointerup` 时量位移，超过 `TAP_SLOP`（10px）或按住超过 `TAP_HOLD`（700ms）就当滑动。手机上的滑动页面必然先触发 `pointerdown`，若在那里就进编辑，手指一擦过某行就开编辑并弹键盘，页面再也滚不动。桌面与手机共用同一套阈值（`onTap` / `onTapOutside`）。
- **静止态 DOM 只多三个节点**：顶栏 `#planBtn`（桌面入口）、手机端 `#mTabs` 与 `#mPlan`（窄屏入口）。手机端那两个在桌面是 `display:none`，但仍在 DOM 里，所以基线变更是 `+37 / -8`。窗口本身只在打开时渲染——拖拽态三格用的是同一个思路。

## Considered Options

- **以周为键的对象 `{"2026-W46": [{...}]}`**：读一周很直接，但每条记录就没有自己的 `id`，改一条要「周 + 下标」定位；下标在删除后会漂。放弃。
- **规划存成一段自由文本**：最初的方向。但用户要「一行一条、能打勾划掉」，文本做不到逐条状态。放弃。
- **规划嵌进周轴纸里（纸内页眉）**：视觉最统一，但纸高会被永久推高，且它和「安排」挤在同一张纸上会让人以为规划也能拖。放弃。
- **页边侧标 / 纸外横带**：一个太隐蔽（不点开看不见，与「清晰看到」冲突），一个占首屏三分之一。放弃。
- **规划走 `/api/items` 的同一张表，加 `kind: 'plan'` 区分**：所有 `items` 查询都要多一个过滤条件，漏一处就会把规划画进周轴。两张表更安全。放弃。

## Consequences

- **`/api/export` 返回磁盘格式**：`forDisk()` 把空的 `plans` 省掉，导出文件能原样放回 `DATA_DIR`。这条是 smoke 抓出来的——最初直接 `res.json(store.load())`，导出里凭空多了 `plans: []`。
- **`envelope()` 的 5 个调用点全部要带 `plans`**：漏一个就会在保存安排时把规划整块抹掉。这是两张表共用一封信封的代价。
- **顶栏不算「点外面」**：规划窗开着时点翻周按钮，窗口该跟着换内容而不是被关掉。`onTapOutside` 的排除列表是 `.pw, .bar`。
- **`.ico` 必须显式给宽高**：只有 `viewBox` 的 SVG 按 300×150 渲染，一个 14px 的加号会撑成 281px，把列表挤到 4px 高——这次真踩了，自检抓出来的。
- **`justEditedAt` 是必要的脏招，但它指向一个真实约束**：浏览器的 `focusout` 先于 `pointerup` 执行，等到点外面的回调跑起来时 `planUi.editId` 已经被清空，光看它分不清「这一下是退出编辑」还是「这一下要关窗」。所以在 `leave()` 里记一笔时间戳，500ms 内不再关窗。更干净的做法是让编辑退出与关窗走两条独立的事件源，但那要改 `focusout` 的时机，风险更大。
- **勾选要同时刷两处**：`setPlanDone()` 原来只查桌面浮窗的 `.pw-row`，手机端 `.mrow` 不会变。两边各有一份行节点，`paint()` 要在两个作用域各跑一遍。
- **新增自检 `npm run smoke:plan-mobile`**：14 项，视口 390 宽、真触屏事件（`Input.dispatchTouchEvent`）。覆盖「滑动不进编辑」「轻点进编辑」「点空白保存」「勾选落盘」「两页切换」。
- **DOM 基线变更 `+37 / -8`**：手机端的 `#mTabs` 与 `#mPlan` 在桌面虽被 `display:none` 隐藏，但仍占 DOM，所以基线里会出现。这是有意的常驻节点，理由与 `#planBtn` 相同。
